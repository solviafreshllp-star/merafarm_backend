# MeraFarm Backend — Task List

NestJS + Prisma + Postgres + Redis/BullMQ, `merafarm/backend`. This is the backend-only slice of the full plan at [`../TASKS.md`](../TASKS.md) — see that file for the frontend tasks and infra items. Media storage decision: [`../MEDIA-STRATEGY.md`](../MEDIA-STRATEGY.md). The frontend design/behavior spec these endpoints need to support is at [`../frontend/DESIGN.md`](../frontend/DESIGN.md).

**Decisions locked in** (see `../TASKS.md` for the full log): cart uses a backend `Cart`/`OrderGroup` model (one payment per multi-campaign cart); admin role is a simple `isAdmin` boolean for now, with real RBAC deferred (flagged in Phase 2); media storage is Cloudflare (R2 + Images + Stream), rolled out in phases; the admin panel is full-scope (user management, notifications, campaign approval, live campaign editing, refund management) — see Phase 1.5 below.

## Phase 1 — Core Missing Features (buyer/seller side)

- [x] **1.1 OTP store → Redis.** `src/auth/otp.service.ts` now writes/reads OTPs in Redis (`otp:<phone>`, 5-min TTL via `SET ... EX`) using the same `ioredis` dependency BullMQ already needs. **Status: DONE, with a documented fallback.** This machine has no Redis instance running at all (no Docker, no native Windows build, and `choco install memurai-developer` failed — this session's shell isn't elevated, so the install needs to be run manually from an admin PowerShell: `choco install memurai-developer -y`, or install Docker and run the `redis` service already defined in `../docker-compose.yml`). Per the user's instruction (2026-10-14) to keep testing unblocked either way, `OtpService` tries Redis first (short `connectTimeout`/`maxRetriesPerRequest` so it fails fast, not hangs) and transparently falls back to the original in-memory `Map` if Redis is unreachable, with a logged warning each time. Verified end-to-end over HTTP (request-otp → verify-otp → JWT) using the fallback path. Once Redis is actually running, no code change is needed — it'll just start using it.
- [x] **1.2 Order-expiry job.** Added `src/jobs/order-expiry.service.ts` — an `@nestjs/schedule` `@Cron(EVERY_MINUTE)` job (not BullMQ — no delayed-job-per-order bookkeeping needed, and it doesn't depend on Redis being up, unlike the refund queue). Scans both stale `OrderGroup`s and stale standalone `Order`s (`orderGroupId: null`) past `ORDER_EXPIRY_MINUTES` (default 15), decrements `bookedUnits` and sets `CANCELLED` inside one Prisma transaction per group/order, then broadcasts the new campaign state over the socket. **Status: DONE, verified via integration test** (`test/integration/order-expiry.spec.ts`, see 1.18) — confirms a stale standalone order AND every order under a stale `OrderGroup` get cancelled together with `bookedUnits` released, while a fresh order is left alone. A live-server attempt to verify this by backdating a row with raw `psql UPDATE ... now() - interval '20 minutes'` gave a false negative — the column is `timestamp(3)` *without* time zone, so the session-local (IST) wall-clock value got written with no tz marker, and the app then read it back assuming UTC: a ~5.5h skew that made the "stale" row look like it was from the future. The integration test avoids this entirely by going through Prisma's own `Date` handling, which is the trustworthy result here — worth remembering if anyone else tries to backdate a row via raw SQL against this schema.
